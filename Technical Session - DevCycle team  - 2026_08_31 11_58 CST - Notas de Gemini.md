### **Detalles**

* **Objetivos de la sesión**: El propósito principal de la reunión fue lograr que todos los líderes de los tracks expusieran sus avances y visualizaciones sobre la arquitectura y la interfaz de usuario (front-end). El objetivo es homologar el entendimiento de los diferentes tracks, discutir cómo se están diseñando y determinar si es necesario trabajar de manera estandarizada para consolidar un frente común.

* **Equipo de interfaz de usuario**: Se discutió la integración de Javi Enrique Trejo para liderar el desarrollo del front-end, junto con la incorporación de integrantes adicionales para robustecer el equipo. Se mencionó que el objetivo es acelerar el trabajo evitando esperas innecesarias. Se confirmó que, si el requerimiento ya está siendo cubierto, no es necesario realizar gestiones adicionales con Jorge.

* **Expectativas del proyecto**: Se debatió la necesidad de definir claramente la expectativa del proyecto, ya que existen diferentes visiones sobre cómo unir las iniciativas. Se planteó la duda de si se requiere un único front-end centralizado o si es más eficiente que las aplicaciones existentes se comuniquen entre sí, considerando que la experiencia de usuario debe ser el factor determinante.

* **Rol del Group Product Owner**: Se enfatizó la importancia de contar con un rol de Group Product Owner para representar la visión del producto, consolidar el entregable para el negocio, y alinear las prioridades del sponsor. Se destacó que este rol es necesario para que todas las decisiones y respuestas provengan de una sola línea estratégica.

* **Integración con Monday**: Se discutió la expectativa de integrar el proyecto dentro de Monday, reconociendo que muchas de las aplicaciones construidas originalmente no fueron diseñadas pensando en esta integración. Se subrayó la necesidad de decidir si se busca una integración total o si se conservarán las aplicaciones existentes, manteniendo siempre la transparencia para los interesados de las oficinas de proyectos.

* **Colaboración con el equipo de Gus Vargas**: Se propuso integrar al equipo de Gus Vargas al desarrollo del front-end para aprovechar su conocimiento técnico, ya que ellos fueron quienes desarrollaron las librerías y la base de datos de los elementos de experiencia de usuario. Se acordó que sumar a este equipo ayudará a evitar retrabajos cuando llegue el momento de la integración total.

* **Revisión de tracks de trabajo**: Se realizó un ejercicio para identificar y mapear los tracks existentes, comenzando con el track de "Registro de Iniciativa". Se aclaró que este track inicial debe interactuar con el usuario para consultar el contexto de proyectos existentes y proporcionar retroalimentación durante el registro, sirviendo como base para el flujo completo.

* **Automatización de estimaciones (Calculadoras)**: Se presentó el funcionamiento de la aplicación asistida para estimaciones, la cual utiliza NextJS, JavaScript y Gemini como motor de inteligencia artificial. Este sistema analiza los requerimientos del usuario (brief), consulta la API de Google Cloud para infraestructura (Building API), y considera servicios externos para generar una hoja de costos detallada (charter), aunque todavía requiere optimizaciones en la capa de servicios externos.

* **Flujo del proceso y dependencias**: Se mapeó la secuencia del flujo de trabajo, que incluye el registro de la iniciativa, el comité de ideas, el comité de diseño, la generación de hojas de costos, y la solicitud de números de PEP ante contraloría. Se identificó que cada etapa genera entregables específicos (como el canvas o la hoja de costos) que sirven de insumo para las etapas siguientes.

* **Unificación de la visión del proyecto**: Se aclaró que el proyecto ya no debe verse como esfuerzos aislados, sino como un solo proyecto unificado que automatiza el proceso de punta a punta. Se reconoció que, aunque anteriormente cada equipo tenía sus propias fases, estas deben ajustarse al diagrama unificado para asegurar la cohesión.

* **Clarificación de insumos y entregables**: Se discutió la necesidad de comprender los insumos y salidas de cada equipo, como el uso de templates para la creación de Request for Services (RFS). Se acordó que es vital que cada equipo defina qué información necesita consumir de los demás para evitar ambigüedades en la entrega final.

* **Planificación de sesiones de seguimiento**: Se acordó realizar sesiones adicionales para mapear el flujo a detalle utilizando una dinámica presencial o remota con cámaras encendidas para mejorar la interacción. Se definió que el próximo esfuerzo se enfocará en aterrizar los procesos en un diagrama claro para poder avanzar con la planificación.
